# MÓDULO B2C — CLIENTE

## Sistema Web Integral de Gestión Operativa y Venta de Pasajes Interprovinciales

### LOS CHASKIS

---

# 1. OBJETIVO DEL MÓDULO B2C

Implementar el portal público de **LOS CHASKIS**, orientado a clientes que desean consultar viajes disponibles, seleccionar sus asientos, registrar los datos del pasajero, realizar un pago simulado y obtener la confirmación de su reserva y comprobante.

El flujo debe mantenerse estrictamente en el siguiente orden:

```text
INICIO
  ↓
BÚSQUEDA DE VIAJE
  ↓
RESULTADOS
  ↓
SELECCIÓN DE VIAJE
  ↓
SELECCIÓN DE ASIENTO
  ↓
DATOS DEL PASAJERO
  ↓
COMPROBANTE
  ↓
PAGO SIMULADO
  ↓
CONFIRMACIÓN
  ↓
VOUCHER / COMPROBANTE
```

## REGLAS GENERALES

* No modificar el flujo indicado.
* No agregar pasos adicionales al proceso de compra.
* No eliminar ninguna funcionalidad especificada.
* Mantener las cuatro vistas principales:

  * `inicio.html`
  * `resultados.html`
  * `compra-pasaje.html`
  * `confirmacion.html`
* Utilizar los datos disponibles en MySQL.
* El frontend debe implementarse con **HTML + JavaScript + Bootstrap 5**.
* El backend debe utilizar **Spring Boot + Spring Security + MySQL**.
* El pago es **simulado**; no integrar una pasarela de pago real.
* Mantener el sistema preparado para clientes registrados y clientes invitados.
* Los datos de compra deben persistirse en la base de datos.
* Validar los datos antes de avanzar al siguiente paso.
* La disponibilidad de asientos debe reflejar el estado real del viaje.

---

# 2. `inicio.html`

## LANDING PAGE + BUSCADOR PRINCIPAL

Esta es la puerta de entrada pública del portal B2C.

El usuario debe poder consultar rápidamente un viaje indicando origen, destino, fecha y cantidad de pasajeros.

---

## 2.1. HERO SECTION

Crear un banner principal institucional de **LOS CHASKIS**.

Debe incluir:

* Imagen representativa de la marca.
* Lema comercial.
* Diseño visual relacionado con transporte interprovincial.
* Buscador principal superpuesto sobre el Hero Section.

El buscador debe ser el elemento principal de interacción de esta sección.

# 4. `compra-pasaje.html`

## MAPA DE ASIENTOS + DATOS DEL PASAJERO + COMPROBANTE + PAGO

Esta es la pantalla principal del proceso de compra.

Debe concentrar en una misma vista:

1. Selección de asiento.
2. Datos del pasajero.
3. Datos de facturación/comprobante.
4. Método de pago.
5. Resumen económico.
6. Finalización de la reserva.

No dividir estas funcionalidades en nuevas pantallas.

---

# 4.1. MAPA / CROQUIS INTERACTIVO DEL BUS

Representar visualmente la distribución de asientos.

Si el bus tiene más de un piso, mostrar:

```text
PISO 1
PISO 2
```

según corresponda.

La distribución debe obtenerse de:

```text
asientos
```

---

## Estados visuales de los asientos

Utilizar:

```text
DISPONIBLE → Verde
SELECCIONADO → Azul
OCUPADO / VENDIDO → Rojo
```

---

## Leyenda de ubicación

Mostrar la ubicación correspondiente:

* Ventana
* Pasillo

La información debe relacionarse con el campo de ubicación del asiento.

---

## Selección

El cliente debe poder seleccionar los asientos disponibles.

Los asientos ocupados/vendidos no deben poder seleccionarse.

El sistema debe evitar seleccionar un asiento que ya fue vendido.

---

## Tipo de Documento

* DNI
* CE
* Pasaporte


## Nombres y Apellidos

Solicitar:

```text
Nombres completos
Apellidos completos
```

## Teléfono

Solicitar teléfono de contacto.

## Correo Electrónico

Solicitar correo electrónico.

Este dato será utilizado para el envío de:

* voucher

* comprobante

# 4.3. SECCIÓN DE FACTURACIÓN / COMPROBANTE

# 4.4. PASARELA DE PAGO SIMULADO

El sistema debe utilizar un proceso de pago **simulado**.

No implementar una pasarela bancaria real.

Los métodos disponibles deben obtenerse de:

```text
metodos_pago
```

* Yape
* Plin
* Tarjeta de Crédito/Débito

---

## Yape / Plin

Cuando el usuario seleccione Yape o Plin:

Mostrar:

* Código QR simulado.
* Campo para ingresar número de operación.

---

## Tarjeta de Crédito/Débito

Mostrar los campos correspondientes para realizar la simulación del pago.

El proceso no debe conectarse a una pasarela real.

---

# 4.5. RESUMEN DEL PRECIO

Mostrar claramente:

```text
Subtotal
IGV (18%)
Monto Total
```

El total debe calcularse a partir del precio del pasaje y la cantidad de pasajes seleccionados.

Mostrar los valores en:

```text

```

---

# 4.6. FINALIZAR COMPRA

Botón principal:

```text
PAGAR Y FINALIZAR RESERVA
```

Al hacer clic:

1. Validar los datos del pasajero.
2. Validar el asiento seleccionado.
3. Validar el tipo de comprobante.
4. Validar el método de pago.
5. Procesar el pago simulado.
6. Registrar la venta.
7. Registrar el detalle de venta.
8. Registrar el comprobante.
9. Actualizar la disponibilidad del asiento.
10. Generar el código de reserva.
11. Redirigir a:

```text
confirmacion.html
```

# 7. REGLAS FUNCIONALES IMPORTANTES

### Disponibilidad

Los asientos vendidos no pueden volver a seleccionarse.

### Reserva

La selección realizada debe mantenerse durante el proceso de compra.

### Venta

Una compra exitosa debe generar los registros correspondientes en la base de datos.

### Comprobante

Debe generarse el comprobante seleccionado:

```text
Boleta
```

o:

```text
Factura
```

### Pago

El pago es exclusivamente simulado.

No integrar:

* Niubiz
* Izipay
* Stripe
* PayPal
* APIs bancarias
* ninguna pasarela real

### Cliente registrado / invitado

El flujo debe permitir la compra para:

* cliente registrado
* cliente invitado

manteniendo el registro correspondiente del pasajero.

### Confirmación

Después de finalizar correctamente la compra, el usuario debe terminar en:

```text
confirmacion.html
```

No redirigir directamente al login ni a otra pantalla.
